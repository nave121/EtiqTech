# Layer 3 context: measured breakdown and options

`docs/dev-log/layer3-context-options.md` | review memo, 2026-09-05 | recommendation only, nothing implemented (this is a review-behaviour change and the repo was read-only for this pass)

## The problem in one paragraph

Layer 3 (`src/llm_layer3.py`) assembles one prompt out of a fixed grounding block plus the protocol. With `OLLAMA_NUM_CTX=32768` and `LLM_MAX_TOKENS=8192` the budget is 24,576 tokens, warning at 20,890 (`src/llm_clients.py:171-201`, `estimate_tokens` is `len // 4` at line 164). The fixed block alone is 20,839 estimated tokens, 99.75% of the warning line, before any protocol text. On a median protocol the prompt overflows the budget; on the largest example it exceeds `num_ctx` itself and Ollama truncates the prompt with no error, so Layer 3 reviews a protocol it never fully saw.

## Measured breakdown

Real tokens at 4.09 chars/token: 27,645. Output room left: 32,768 minus 27,645 = 5,123 of the 8,192 requested (62.5%), so on this fixture the model is already output-squeezed, not truncated. Four more experiments of this size (5,916 chars each) would put the prompt past `num_ctx` (33,431 real); three still fit (31,984).

Sub-breakdowns that matter:

- Protocol JSON: `summaries` 13,521 chars (55% of it), of which `summaries._sub_questions` (6,801 chars as JSON, 1,700 tokens) is a verbatim duplicate: all six sub-fields are substrings of `summaries.scientific_en_≤300w`. That field holds 928 words against its own 300-word name; nothing enforces the cap.
- Catalog: 6 entries, ~2,425 chars each; the `examples` arrays are 10,248 of 14,553 chars (`DEFAULT_MAX_EXAMPLES=3`, `MAX_SNIPPET_CHARS=800`, `src/xmeta_catalog.py:16-17`). Projecting to `{path: x_meta}` with compact separators measures 2,758 chars / 689 tokens.
- Case reports: GLOBAL 4,937 + 13 files at 1,340 to 1,798 chars = 25,717 raw, 26,245 assembled. Grows with every head-to-head pair added.

Distribution across the 94 parsed examples (protocol JSON only, est tokens): min 1,509 / median 6,179 / p90 9,353 / max 24,290. Whole prompts: `examples/demo_instance.json` pass 1 = 24,355, pass 2 = 23,936 (past the warning line, at the budget). `examples/head-to-head/3/bad.html` pass 1 = 47,466, pass 2 = 50,391 (past `num_ctx`; truncated today). Pass 2 with an empty pass-1 result measures 112,402 chars / 28,100 tokens on the good fixture, and a real pass 2 adds pass-1 findings and Layer 2 verdicts on top, so pass 2 is larger than pass 1 in production.

Two arithmetic consequences that rank the designs: the fixed block is ~21.7k of the problem, but the p100 protocol is 24.3k on its own. Any design that keeps the whole instance in one prompt cannot hold 24k at p100. Designs A and C hold to about p90. Only B holds at p100.

Two constraints on every design:

- The retrieval corpus is guidance only: `resources/corpus/guidance_il.jsonl`, 89 chunks, all `doc_type: guidance_section`, 46 EN + 43 HE, 65,725 chars. The EN half is the chunked `the_law-english_translation.txt`, so retrieval can replace that block with no new corpus. Case reports and the x_meta catalog are in no corpus. The `norina_record` / `threer_guide` / `prepare_section` doc_types in `THEME_GROUNDING` match nothing today.
- Grounding is opt-in (`ETIQTECH_GROUNDING`, off by default). Every design needs an off-path, and it cannot be "fall back to the full block" or the budget goal disappears when the flag is off.

## Side findings, flagged not fixed

1. **Fail-open in the fallback.** `_fallback_pass1()` returns `{"sections": []}`, which `_derive_pass1_assessment` turns into `("approve", "low")` (`src/llm_layer3.py:276-303`). A Layer 3 pass that errored reads as a clean bill in `disagreement_summary`. Fix before any design ships: the fallback should carry a sentinel section (`status: "Information Missing"`, `severity: "Major"`) so an error can never derive "approve".
2. **`LAYER3_SAMPLING_RATE` is documented but unimplemented.** `README.md:163` lists it as a supported env var (default 0.10); `tests/test_privacy_canary.py:57` and `tests/test_gunicorn_sessions.py:46` set it. No Python reads it; `should_trigger_layer3(..., sampling_rate=0.10)` is never overridden by a caller. The tests pass on `force=True`.
3. **x_meta catalog coverage gap.** `HIGH_LEVERAGE_PREFIXES` (`src/xmeta_catalog.py:166-177`) lists 8 paths; `load_high_leverage_catalog()` returns 6. `experiments.[].severity_level_1_to_5` and `experiments.[].analgesia` have no `x_meta` block in IACUC_SCHEMA_V2 and are silently dropped. The pass-1 rubric grades exactly those two (sections 4 and 6) with no reference examples. Zero tokens, real coverage loss.
4. **Article citations have no source.** The prompt demands `regulatory_basis` in the form "Israeli Law Art. 17(b)", but the statute is not in the prompt or the repo (memo 1). Those citations come from model memory today.

## Design A: retrieval replaces the guidance block and the case reports

Code, all in `src/llm_layer3.py`: add a 9-entry `LAYER3_SECTION_GROUNDING` keyed by the prompt's section names, queries copied from `llm_agent.THEME_GROUNDING` (12 themes; 6 map cleanly; severity, monitoring and analgesia all collapse into the single theme `severity_monitoring_analgesia` and need splitting). Add `_retrieve_layer3_grounding(instance)` shaped like `llm_agent._retrieve_grounding` (lines 321-345): `k=3` per section, dedupe on id, species filter, cap the union at 10, never raise. In `_build_layer3_blind_context` swap `_load_full_law_text()` and `_load_all_case_reports()` for `format_grounding_block(hits, max_chars_per_hit=1200)` (chunks run to `MAX_CHARS=1600` at `scripts/build_law_corpus.py:33`; the 700 default cuts them mid-section). Off-path when grounding is disabled: `llm_agent._load_law_text(max_chars=6000)` + `_load_case_reports(max_chars=2000)`, about 2,000 tokens. Plumb `grounding` and `grounding_notice` into `_build_final_result` and `HumanEyeResult` (`src/contracts.py:160`, mirroring `VerifierResult.grounding_notice` at :131) and yield a `warning` event as `run_verification_stream` does at `llm_agent.py:1183-1185`.

Savings: 17,201 tokens become ~3,000. Pass 1 lands at ~9,900 (demo), ~17,000 (p90), ~32,000 (p100, still over).

Losses: guidance the 9 static queries do not reach (off-form protocols such as field studies); the case reports entirely, and `GLOBAL_ETHICS_REPORT.md` has no substitute in any corpus; article-number precision gets worse, since chunk titles carry section paths, not article numbers (already a problem, see side finding 4).

Tests: new budget regression asserting `estimate_tokens(_build_pass1_prompt(bad.html)) < 24_576`. Layer 3 twins of `tests/test_retrieval.py:116` (off by default) and `:143` (degraded notice reaches the stream). `tests/test_privacy_canary.py` must patch `src.llm_layer3.get_retriever` or the run hits a real `/api/embed`; queries are static strings, so this is network hygiene, not a leak. `test_layer3_contracts.py` and `test_e2e_pipeline.py` unaffected (still 2 calls).

Risk to the additive contract: none to the coded contract (`test_additive_union`; `_build_final_result` unchanged). The exposure is recall: findings the model cannot make because the evidence left the prompt. Euthanasia is the weakest section; Layer 2 has `_build_avma_grounding_block` and Layer 3 has no equivalent. Worth porting (~200 tokens, species-conditional).

## Design B: per-section passes, then synthesis

Code: `LAYER3_SECTIONS`, one entry per prompt section with an `instance_slice` callable, queries and doc_types. Approximate slice sizes on the p100 protocol (24,290-token instance), est tokens: scientific justification ~4,100; alternatives ~150; animal numbers ~4,700 to 4,800; severity ~3,400; monitoring and endpoints ~2,100; analgesia and anesthesia ~500; euthanasia ~1,400 to 1,500; personnel 638; housing ~450 to 500. (A second measurement of the same stated key sets landed 1 to 17% below the first on every row except personnel; the exact slice definitions need to be published with the code. The conclusion, worst section far under budget, holds either way.) `_build_section_prompt` = rubric header + slice + `format_grounding_block` at `k=3` for that section (~900 tokens). Worst-case section prompt ~5,900 tokens; median protocol ~2,500. `_protocol_digest(instance, cap=300)` for synthesis: 3,809 tokens on p100, 608 on demo. Synthesis prompt = pass-2 rubric + digest + concatenated section verdicts + failing checklist items (3,344 on the big one), about 9,000 worst case. `run_human_eye` loops sections, concatenates, then synthesises; `_derive_pass1_assessment` and `_build_final_result` take the concatenated list unchanged. Streaming needs a section identifier on `pass_start` / `pass_done`.

Savings: max single prompt ~9,000 tokens, and it is the only design where p100 fits. Cost: 10 calls instead of 2, roughly 5x wall-clock on local Ollama, and 10 chances at a JSON parse failure.

Losses: cross-section findings that need two sections' full text. "Severity 1 but survival surgery without analgesia" is the `procedure_timeline` x `analgesia` pair; no per-section pass sees both, only the digest does, at 300 chars per field. `analgesia`, `anesthesia`, `euthanasia`, `humane_endpoints` must stay uncapped in the digest (they are small: ~2,000 tokens for all 8 experiments on p100).

Tests: `tests/test_layer3_contracts.py:180-215` breaks (asserts exactly 2 `pass_start` and 2 `pass_done`); `tests/test_e2e_pipeline.py:188` breaks (2-element `side_effect`, needs 10). New: every `instance_slice` output is a subset of the instance, and the union covers every field the 9 sections claim to review.

Risk to the additive contract: highest of the three, and it multiplies side finding 1. Nine section calls means roughly 5x the odds that one pass silently drops its findings, and the drop is invisible in the result. Fix the fallback first.

## Design C: one pass, catalog and case reports trimmed, protocol capped

Code, in `_build_layer3_blind_context`: catalog projected to `{e["path"]: e["x_meta"]}` with compact separators, 3,638 to 689 tokens (Layer 3 grades, it does not draft, so shape examples earn nothing here). Case reports: either a new `scripts/build_case_corpus.py` writing `resources/corpus/cases_h2h.jsonl` with `doc_type: case_report` (25,717 chars, ~16 chunks at 1,600) and `k=4 x 1200 chars` ≈ 1,200 tokens, or the honest non-retrieval version `llm_agent._load_case_reports(max_chars=2000)` (500 tokens), labelled as a trim, not as grounding. Protocol: a `_compact_instance` helper with four moves, measured: compact separators plus null-prune gives p100 24,290 to 21,298 and demo 2,264 to 1,578; drop `pi.id_type/id_number/phone_*/email`, `participants[].id_number/phone/email`, `pi_declaration`, `*.attachments` (no ethics finding depends on them and they are the PII the canary chases); cap `summaries.scientific_en_≤300w` (2,735 tokens on p100), `n_justification.details` (3,599) and `experiments[].procedure_timeline` (3,275 across 8 experiments) at ~1,200 chars with a marker; never cap `analgesia`, `anesthesia`, `monitoring`, `humane_endpoints`, `euthanasia`. Also drop `summaries._sub_questions` (1,700 tokens, pure duplicate).

Savings: catalog −2,949, case reports −5,361 (or −6,061 trimmed), protocol −12% to −30% plus caps. Pass 1: demo ~16,300, p90 ~24,100 (at the ceiling), p100 ~36,000 (over), because C keeps the 10,640-token guidance block. Smallest diff, weakest guarantee.

Losses: x_meta examples (the linter already checks those 6 fields, low marginal loss); the tails of three free-text fields, and the tail of `procedure_timeline` is exactly where an unflagged painful step hides. This is C's real recall risk.

Tests: no structural test breaks. New: `_compact_instance` never invents a key, PII keys are gone, capped fields end in the marker; plus the same budget regression. `test_privacy_canary.py` gets stronger, no change needed unless the case corpus is added (then patch `get_retriever`).

Risk to the additive contract: lowest. Only exposure is a finding living past a 1,200-char cap.

## The num_ctx option: raise the window instead

Cost, for the default model `qwen3.5:35b`. From the primary config at https://huggingface.co/Qwen/Qwen3.5-35B-A3B/raw/main/config.json (verified): 40 layers alternating 3 linear-attention and 1 full-attention, so 10 full-attention layers; `num_key_value_heads=2`; `head_dim=256`; `max_position_embeddings=262144`. KV bytes per token at f16 = 10 x 2 x 2 x 256 x 2 = 20,480. So the KV cache costs 0.67 GB at 32k, 1.34 GB at 64k, 2.68 GB at 128k, 5.37 GB at 256k. Linear-attention layers hold a fixed-size state that does not grow with length, which is why only 10 of 40 layers are billed. An independent table matches to the byte (https://kaitchup.substack.com/p/the-kv-cache-of-small-moes-qwen3, 2026-03-18, verified; per-model figures inline, consolidated table paywalled). Weights are 24 GB (https://ollama.com/library/qwen3.5, verified), so 128k f16 is ~27 GB total.

Contrast: a dense ~30B model such as Qwen3-32B (https://huggingface.co/Qwen/Qwen3-32B/raw/main/config.json, verified: 64 layers, 8 KV heads, head_dim 128) costs 262,144 bytes/token, 12.8x more: 8.6 GB at 32k, 17.2 GB at 64k, 34.4 GB at 128k. "Can we afford 128k" depends entirely on which local model is running.

Ollama facts (all verified 2026-09-05): default context is chosen by VRAM (<24 GiB: 4k, 24 to 48 GiB: 32k, ≥48 GiB: 256k) and the docs advise "at least 64000 tokens" for agent, coding and search workloads (https://docs.ollama.com/context-length); the FAQ still says the default is 4096, so the docs contradict themselves (https://docs.ollama.com/faq). `OLLAMA_KV_CACHE_TYPE` q8_0 is about half of f16, q4_0 about a quarter, and it is global to all loaded models; `OLLAMA_FLASH_ATTENTION=1` reduces memory as context grows; parallel requests multiply the context allocation ("Parallel request processing for a given model results in increasing the context size by the number of parallel requests"), which matters because the repo ships a gunicorn server: budget `num_ctx x parallelism`. `ollama ps` shows the allocated context and the CPU/GPU split. Neither Ollama page documents the prompt-truncation semantics the repo measured at `llm_clients.py:174`; keep the repo's pre-flight warning regardless. All qwen3.5 and qwen3.6 variants list a 256K window (https://ollama.com/library/qwen3.5, https://ollama.com/library/qwen3.6); plain qwen3 is uneven (40K for 0.6b/1.7b/8b/14b/32b, 256K for 4b/30b/235b, https://ollama.com/library/qwen3).

Apple Silicon: the binding limit is wired memory, roughly 75% of RAM by default, adjustable with `sudo sysctl iogpu.wired_limit_mb=<mb>`, non-persistent across reboots (https://github.com/ggml-org/llama.cpp/discussions/2182, verified). 24 GB weights + 2.7 GB KV fits a 48 or 64 GB Mac and does not fit a 32 GB Mac at the default limit; there, use q8_0 KV or `qwen3.5:9b`. Data point from a fetched thread (cited as QwenLM/Qwen3.6 #139, served as QwenLM/Qwen3.8 #139, https://github.com/QwenLM/Qwen3.6/discussions/139, verified): M4 Ultra 128 GB running an 80B-A3B model at Q8_0 with 3 x 128K slots at 92.5 GB wired, "tight but stable"; cold 60K prefill ~80 s vs ~1.0 s warm. Prompt-prefix stability is worth more than window size on that hardware. NVIDIA: no unified-memory escape; past VRAM, layers spill to CPU and throughput collapses. On a 24 GB card with a 24 GB q4 model there is no room for a 128k f16 cache; q8_0 KV or a smaller weight quant is required (my estimate from vendor-documented behaviour, not benchmarked).

Why a bigger window does not fix fidelity: Chroma's Context Rot report (Hong, Troynikov, Huber, 2025-07-14, 18 models including Qwen3-32B, https://www.trychroma.com/research/context-rot, verified) finds performance "grows increasingly unreliable as input length grows"; distractors compound; models under-generate and stop early on long tasks (the failure mode of "review every section and report all findings"); and models do worse when the haystack "preserves a logical flow of ideas", which a structured protocol does. "Lost in the Middle" (Liu et al., TACL 2023 per the arXiv page, https://arxiv.org/abs/2307.03172, snippet-verified): accuracy is highest when the relevant text sits at the start or end and degrades in the middle; operational rule for the prompt builder is to put the retrieved guidance and the section under review at the two ends. Databricks Mosaic, "Long Context RAG Performance of LLMs" (https://arxiv.org/pdf/2411.03538): the abstract states that "only a handful of the most recent state of the art LLMs can maintain consistent accuracy at long context above 64k tokens"; the more specific figures circulating (2,000+ experiments, ~32k/~64k thresholds, DBRX 5.2% to 50.4%) are not in the abstract and remain unverified until someone reads the PDF. Map-reduce over sections is the best-evidenced structural fix: Chain of Agents (NeurIPS 2024 per the Google Research write-up https://research.google/blog/chain-of-agents-large-language-models-collaborating-on-long-context-tasks/, paper https://arxiv.org/abs/2406.02818, snippet-verified) and ToM, tree-oriented map-reduce over a document's heading tree (EMNLP 2025 Main, https://arxiv.org/abs/2511.00489, verified), which beats both divide-and-conquer and RAG baselines on 70B+ models. A protocol with numbered sections already has that tree. Passing a compacted structured digest of layer N-1 into layer N rather than transcripts is the same idea Anthropic ships as compaction (https://platform.claude.com/docs/en/build-with-claude/compaction, snippet-verified).

## Ranked recommendation (for the maintainer to decide)

0. **Before anything: fix the two pre-existing defects.** `_fallback_pass1` must not derive "approve" (side finding 1), and `LAYER3_SAMPLING_RATE` must either be read or be removed from the README and the two tests (side finding 2). Both are small, both are independent of the design choice, and B in particular is unsafe without the first.
1. **Stop the bleeding today: raise `OLLAMA_NUM_CTX` to 65536 and keep the pre-flight warning.** Cost on the default model is ~0.67 GB of extra KV at f16 (or ~0.34 GB with `OLLAMA_KV_CACHE_TYPE=q8_0`), times the gunicorn parallelism. Pass 1 on the largest example (47,466 + 8,192 output = 55,658) then fits without truncation. This matches Ollama's own ≥64k guidance. It is a mitigation, not the fix: the fidelity evidence above says the model reviews a 47k prompt worse than a 14k one, and any design below still applies. Do not chase 128k or 256k for this workload.
2. **Ship A plus C's compaction items (call it A′).** Retrieval replaces the guidance block and the case reports; catalog projected to `x_meta`; instance pruned, compacted, PII-stripped, `_sub_questions` dropped. Pass 1 lands at ~7,000 (demo) / ~14,000 (p90) / ~29,000 (p100). One prompt, 2 calls, existing tests survive, budget cleared for about 90% of real protocols. Add the budget regression test on `head-to-head/3/bad.html` in the same change. Also add the statute (memo 1) to the corpus so `regulatory_basis` citations have a source; without that, step 2 makes article citations no worse but also no better.
3. **Add B as a budget-triggered fallback, not the default.** At the top of `run_human_eye`: if `estimate_tokens(p1_prompt) > 0.85 * available`, run the section loop; otherwise the single pass. That covers p100 without paying 10 calls on median protocols, and it is the only path that fixes truncation structurally once step 1's headroom is exhausted by protocol growth. Requires the two broken tests to learn about section events.
4. **C alone: not recommended.** Take its parts (already inside step 2); its shape cannot reach the target while the 10,640-token guidance block stays.

Decision needed from the maintainer: (a) accept the A′ design as the review-behaviour change, which changes what evidence Layer 3 sees per protocol and therefore what it can find; (b) whether B's budget trigger is wanted in the same change or after; (c) whether `OLLAMA_NUM_CTX=65536` becomes the code default in `src/llm_clients.py` or stays an env override in the README, given the parallelism multiplier on a shared Ollama host.
